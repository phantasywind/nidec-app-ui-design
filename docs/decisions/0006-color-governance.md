# ADR-0006：集中颜色治理与品牌值批准边界

- 日期：2026-09-05。
- 状态：Locke 已授权集中颜色治理实施；具体共享品牌色表/Fluent状态映射待确认。
- 目的：让未来换肤主要改变集中配置，而不是逐个组件重写。

## 所有权和唯一来源

共享库管理颜色角色、主题映射、使用约定和检查；应用管理业务状态如何对应语义角色。不要把审批/报价/工程生命周期颜色映射放进共享库。

主题分为三层：原始配色（具体色值和来源）、语义角色（品牌交互/文字/背景/边框/反馈/焦点）、Fluent token映射。组件只消费主题语义，不直接写品牌色值。颜色主题与间距、字体等配置分开，避免换色同时改变布局。

正式原始配色必须先记录来源及 Locke 批准。CPQ 当前实现是候选证据，不自动成为 Nidec 全应用品牌批准。两套冲突值不能混合后称为正式标准；状态缺项须标为 pending，不自行猜测。

## 当前落地范围

- `src/index.ts` 中共享组件无品牌颜色字面量，继续由显式 `NidecProvider.theme` 管理。
- 演示 Fluent 主题选择集中在 `fixtures/react-form-batch-consumer/src/themes.ts`，当前仍为官方浅/深主题；不在页面内散落选择/覆盖。
- 演示外壳四种现有颜色集中在 `palette.css`，其他CSS仅引用语义变量；现有视觉值不变。这是演示配置，不是生产主题。
- `scripts/check-colors.mjs` 纳入原 `css:check`，扫描共享src及当前整批演示；除登记的palette外，拒绝常见hex、颜色函数、CSS具名色及JS颜色属性直接值。禁止页面绕过集中主题入口。
- 这是可复核的有界静态检查，不是完整JS/CSS求值器：字符串拼接、计算属性或复杂间接写法仍需代码评审。上游依赖、历史fixture/证据、scaffold生成文件不在本规则范围，不能声称整仓所有颜色已完全归一。
- 不修改公开API、精确依赖、旧tgz、发布阻断或CPQ/EPM代码。现有token/style子路径仍是scaffold，不把本轮demo palette冒充生产token输出。

## 后续正式映射的验收条件

1. Locke 确认色表来源和冲突值；逐个角色记录来源/批准状态。
2. 一处生成或定义完整Fluent状态映射，包括品牌默认/hover/pressed/selected、文字/背景/边框、焦点及success/warning/error/info；不得只修改一个brandBackground并遗漏foreground/stroke。
3. 浅色、深色分开确认；不能把浅色值机械套进深色背景。可先限定批准浅色主题，深色继续明确使用官方测试主题。
4. 文本/状态对比度与禁用、焦点、弹窗、一组完整控件一起复核；通过不等于业务验收。
5. 颜色配置/映射变更与共享包一起版本化。CPQ 接入仍需 Locke 另行批准，由02在main执行。

## 本轮下一道门与回退

候选对照见 `../implementation/color-source-review.md`。尚未认定唯一权威色表前，不把演示换绿或输出名为正式NidecTheme的对象。本轮可安全完成入口集中与检查；正式色表选择是下一项需要用户确认的决定。

回退仅移除本次新增palette/themes/检查及相关引用、文档，恢复演示原有四个色值；保留旧批次源快照和失败证据，不整仓reset。
