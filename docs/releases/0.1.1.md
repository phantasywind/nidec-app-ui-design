## Change type

Visual refinement. No export, prop, type, dependency or peer-version change. No business behaviour change.

| Area | Change | Who is affected |
| --- | --- | --- |
| `ApplicationNavigationItem` | A hovered navigation item now has a subtle grey background (`colorSubtleBackgroundHover`) in addition to the brand-coloured label it already had. | Any application showing the application navigation. |
| `EditableGrid` | The divider line before the frozen Actions column (the last header cell and each action cell) is removed. The column still stays visible and opaque at the right edge when the grid scrolls horizontally. | Applications using `EditableGrid` or the grouped editable grid. When the grid is scrolled horizontally, content now passes under the frozen column without a dividing line. |

## What applications should do

- Re-inspect the application navigation hover state and every Editable Grid after upgrading. Both are visible changes; neither changes behaviour, markup or class names.
- Dependencies are unchanged: `@fluentui/react-components@9.74.7`, `@fluentui/react-datepicker-compat@0.6.39` (only for `/date-picker`), and an exact React / React DOM 19.2.x pair. No lockfile change other than this package is needed.
- Applications that overrode these two styles locally, for example to remove the Actions-column divider or to add a hover background, can delete those overrides after checking the result.

## Adoption after publication

Configure `@phantasywind:registry=https://npm.pkg.github.com` without storing credentials in the repository, then install:

```powershell
npm install --save-exact @phantasywind/nidec-app-ui-design@0.1.1 @fluentui/react-components@9.74.7
# Only when consuming /date-picker:
npm install --save-exact @fluentui/react-datepicker-compat@0.6.39
```

Read the version-matched [adoption guide](../consumer-ui-adoption.md) and [component catalog](../component-catalog.md) at the `v0.1.1` tag. The archive includes dist and README only.

## Publication attempts

### Attempt 1: failed, nothing published (2026-10-09)

[Run 3](https://github.com/phantasywind/nidec-app-ui-design/actions/runs/37982451962), `dry_run` false, `approved_sha256` `e5f755e77d6acf8d1df70a0c012f919c077584c1d768d01ef2a95f9d473a9d3d`, on `main` at `f56bbb0`, started on Locke's written authorization of version 0.1.1 and that hash.

- Both builds, the comparison and the hash check passed. The tag `v0.1.1` was created and pushed to `f56bbb0`.
- `npm publish candidate/*.tgz` then failed with `npm error code 128`: npm read the relative path as a GitHub repository shorthand and tried to fetch it over SSH. The failure happened before any upload. The Release step and the post-publication verification were skipped.
- Nothing was published: GitHub Packages has no `0.1.1`, and the Releases list has no `v0.1.1`. The tag `v0.1.1` exists on the remote and points at `f56bbb0`.
- Cause: a defect in the release workflow written by Claude, not in the package. The fix is `./candidate/*.tgz`, and the tag is now pushed only after publication succeeds, so a failed publication cannot leave a tag behind.
- The workflow refuses a version whose tag already exists. Locke decided on 2026-10-09 to abandon 0.1.1, keep the tag `v0.1.1` untouched at `f56bbb0` (published versions, tags and artifacts are never reused or moved), and release the same content as [0.1.2](0.1.2.md). The tag marks an unpublished version and must not be used as an install reference.

Corrections always use a new version.
